# ОПИС ПРОГРАМИ

Програмний комплекс «AAR» (After Action Review), версія 1.8.0.
Документ складено за структурою ГОСТ 19.402 (ЄСПД) «Опис програми».

---

## 1. Загальні відомості

**AAR** — цифрова платформа операційної розвідки для оборонного підприємства,
що одночасно вирішує два завдання:

1. **Пономерний облік ефективності виробів** — атомарна фіксація кожного
   використання виробу з подальшою автоматичною аналітикою.
2. **Накопичення організаційного досвіду** за методологією NATO Lessons
   Learned — від спостереження до перевіреного уроку із замиканням циклу
   навчання.

Ключова відмінність від класичних систем звітності: платформа не просто
зберігає звіти, а **вимірює й замикає цикл навчання** — бачить повторювану
проблему, допомагає сформулювати причину, призначає відповідального і
перевіряє за фактичними даними, що рішення подіяло.

## 2. Функціональне призначення

### 2.1 Дворівнева модель даних

- **Рівень 1 — Події (`UsageEvent`).** Пономерна подія: виріб, експлуатант,
  дата, результат (успіх / втрата / ремонт), причина за класифікатором,
  ознака аборту (не дійшло до запуску — РЕБ, погода, техвідмова),
  геолокація (GeoJSON). Append-only, ідемпотентність за `client_event_id`.
- **Рівень 2 — AAR-кейси (`AARCase`).** Якісний розбір поверх подій за
  циклом NATO: планувалось / сталось / чому / урок / рекомендації.

### 2.2 Перелік функцій

| Функція | Опис |
|---|---|
| Реєстрація подій | Ручна форма + масовий імпорт CSV/XLSX; offline-first |
| Щоденна довідка | MSR за експлуатантами/типами, деталізація втрат і ремонтів, авто-«Висновки доби» |
| Місячна звітність | Т.4–Т.7: рейтинг за η_c, зони відповідальності, тренди |
| Тригери AAR | T1 падіння MSR_c; T2 повтор причини; T3 аномалія виробу; T4 падіння по підприємству; T5 ручний |
| Цикл кейсу | Жорсткий forward-only перехід станів; аудит кожного переходу |
| Автовалідація | Рекомендація «підтверджена», якщо причина не повторюється N днів; «регресує», якщо повторюється |
| База досвіду | Context-активи draft→validated→deprecated; пошук аналогій лише серед validated |
| Проактивні сигнали | Попередження/ризик/пропозиція до завдання; розгляд; ескалація в кейс |
| Брифінг місії | Агрегація знань за профілем + структурований ШІ-синтез |
| Мета-KPI | Час до валідації, % LI→LL, recurrence rate, навантаження на відповідальних |
| Інтеграції | Вихідні вебхуки з адаптерами під ODIN/DELTA/Кропива/SAP; GeoJSON |
| Аудит | Незмінний журнал із SHA-256 хеш-ланцюгом; перевірка цілісності |
| Експорти №440 | Відомості, акти, журнали за наказом № 440 |

## 3. Опис логічної структури

### 3.1 Архітектура — три шари

```
Шар 3: Контекст-активи (база досвіду) — validated LL, пошук аналогій
        ▲ живить брифінг і аналогії
Шар 2: AAR-кейси — NATO-цикл, рекомендації, автовалідація
        ▲ тригери T1–T5
Шар 1: Пономерні події — append-only, ідемпотентність
```

### 3.2 Компоненти серверної частини (`apps/api/aar_api`)

- `core/` — конфігурація, підключення до БД, безпека (JWT), RBAC, rate-limit.
- `models/` — ORM-моделі (події, кейси, довідники, аудит, контекст, сигнали, користувачі).
- `schemas/` — Pydantic-моделі запитів/відповідей.
- `routers/` — REST-ендпойнти по доменах (16 роутерів).
- `services/` — бізнес-логіка: звіти, тригери, автовалідація, LLM, аудит,
  інтеграції, експорти, брифінг, нотифікації.
- `scripts/` — CLI для cron (генерація звітів, тригери, seed).

### 3.3 Компоненти клієнтської частини (`apps/web/src`)

- `pages/` — 15 сторінок інтерфейсу (дашборд, події, кейси, звіти, брифінг,
  сигнали, цикл навчання, довідники, інтеграції, аудит, налаштування, вхід).
- `lib/` — робота з API, автентифікація (JWT у localStorage), offline-черга (IndexedDB).

## 4. Технічні засоби, що використовуються

- **Backend:** Python 3.12, FastAPI, SQLAlchemy 2 (async), Alembic, Anthropic SDK.
- **Frontend:** React 18, TypeScript, Vite, Workbox (PWA), IndexedDB.
- **Дані:** PostgreSQL 16 (продуктив), Redis 7 (черга), SQLite (тести).
- **Інфраструктура:** Docker, nginx, GitHub Actions (CI), Render (хостинг).

## 5. Виклик і завантаження (розгортання)

1. **Одноклікове (браузер):** Render Blueprint читає `render.yaml`,
   піднімає БД + API + вебклієнт; API самостійно застосовує міграції та
   засіває початкові дані. Детально — `docs/DEPLOY.md`.
2. **Локальне (on-prem):** `docker compose up` в `infra/` піднімає весь контур.
3. **Ініціалізація:** створення адміністратора з env-змінних при першому старті.

## 6. Вхідні дані

- Події використання виробів (ручний ввід або імпорт CSV/XLSX з полями:
  серійний номер, тип виробу, експлуатант, дата, результат, код причини).
- Довідники: типи виробів, експлуатанти, причини втрат (a–д) і ремонтів (а–р),
  зони відповідальності.
- Індивідуальні звіти учасників, проактивні сигнали, контекст-активи.
- Вхідні події від зовнішніх систем через уніфікований REST-приймач.

## 7. Вихідні дані

- Щоденні та місячні звіти (JSON, XLSX, PDF).
- Рейтинг експлуатантів за η_c.
- AAR-кейси з уроками та рекомендаціями.
- Мета-KPI циклу навчання.
- Брифінг підготовки місії (агрегований пакет + ШІ-синтез).
- Форми за наказом № 440.
- Вихідні вебхуки у суміжні системи (GeoJSON / профільні формати).
- JSON-знімок бази для резервного копіювання.

## 8. Методологічна основа (обґрунтування рішень)

- **Дворівнева модель** відповідає NATO-розрізненню «спостереження ≠ урок» —
  дві головні причини провалу LL-програм світу: (1) уроки збираються, але не
  впроваджуються; (2) не вимірюється користь. Платформа закриває обидві.
- **Метрики** MSR (η) = success/launched; MSR_c (η_c) — з поправкою на
  не-обслугові втрати; CLR (λ_c) — рівень втрат обслуги. Розрізнення
  «вузького» і «повного» MSR (з абортами) — за науковою літературою.
- Повне обґрунтування рішень — журнал ADR у `docs/PLATFORM.md` §6.
