# Запуск пілоту AAR — чек-лист і методика базової лінії

> Мета пілоту — не «показати систему», а **отримати власну цифру**: наскільки
> зросли η_c / впала recurrence на РЕАЛЬНИХ даних підрозділу після
> впровадження. Саме ця дельта — головний аргумент для взяття на постачання
> (див. `docs/concept/positioning.md` §5, пункт 2).

## 0. Передумови

- Розгорнутий робочий застосунок (`docs/DEPLOY.md`), не demo.
- Обліковий запис адміністратора (див. розгортання).
- 1 підрозділ-учасник пілоту; визначений відповідальний (OPR).

## 1. Увімкнути AI-функції (для ШІ-синтезу брифінгу і чернеток аналізу)

1. Render → сервіс **aar-api** → **Environment**.
2. Додати `AAR_ANTHROPIC_API_KEY` = ключ Anthropic (console.anthropic.com).
3. Змінити `AAR_LLM_ENABLED` на `true`.
4. Зберегти → сервіс передеплоїться. Перевірити: «Брифінг місії» →
   «Синтез ШІ» має видати реальний результат (не «ШІ вимкнено»).

> Без ключа система працює повністю, крім ШІ-синтезу і LLM-чернеток —
> це нормально, пілот можна вести і без AI.

## 2. Налаштувати довідники під реальні дані

Стартові класифікатори абстрактні (a–д / а–р). Перед пілотом:
- завести реальні типи виробів, експлуатантів, коди причин втрат/ремонтів;
- (на час пілоту прийнятно лишити синтетичні коди, якщо мапінг ведеться окремо).

## 3. Зафіксувати БАЗОВУ ЛІНІЮ (день 0)

До початку активного використання зафіксуйте вихідні показники за
попередній період (напр. останні 30–90 днів) — вручну або імпортом
історичних подій (CSV/XLSX):

| Показник | Де взяти | Значення «до» |
|---|---|---|
| η (MSR) підприємства | Дашборд / Місячний звіт | __ % |
| η_c (crew-adjusted) | Місячний звіт | __ % |
| Recurrence rate | Цикл навчання | __ % |
| Медіанний час до валідації уроку | Цикл навчання | __ днів |
| Топ-3 причини втрат | Щоденна довідка / брифінг | __ |

> Якщо історичних даних немає — базова лінія формується за перші 2–3 тижні
> пілоту, далі порівнюється з наступним періодом.

## 4. Операційний цикл пілоту (щодня / щотижня)

**Щодня:**
- Експлуатанти подають події (форма або імпорт).
- Перед завданням — реєструють проактивні **сигнали** (ризики/попередження).
- Планувальник відкриває **Брифінг місії** за профілем + **Синтез ШІ**.

**Щотижня:**
- Менеджер розглядає авто-відкриті **AAR-кейси** (тригери T1–T5), доводить їх
  циклом NATO до `validated`, призначає OPR.
- Розсилає запити **індивідуальних звітів** учасникам.
- Валідує **контекст-активи** (уроки) — лише validated живлять брифінг.
- Дивиться **Цикл навчання** — чи росте конверсія LI→LL, чи падає recurrence.

## 5. Сповіщення в реальному часі (Telegram) — опційно

Щоб відповідальні отримували алерти миттєво:
1. Створити бота через **@BotFather**, отримати токен.
2. Додати бота у робочий чат/канал; дізнатись `chat_id` (напр. @getidsbot).
3. AAR → **Інтеграції** → «Нова підписка» → тип **telegram**:
   - Chat ID = ваш chat_id; Токен бота = токен від BotFather;
   - події: `aar_case.created`, `signal.created`, `recommendation.auto_validated` тощо.
4. Тепер відкриття кейсу / новий сигнал / підтвердження рекомендації
   автоматично падають у чат.

## 6. Підсумок пілоту (день 60–90)

Повторно зняти ті самі показники (крок 3) → порахувати дельту:

| Показник | «до» | «після» | Δ |
|---|---|---|---|
| η_c | | | |
| Recurrence rate | | | |
| Час до валідації | | | |
| % LI→LL | | | |

**Це і є цифра для постачання.** Дельта на власних даних підрозділу
переконливіша за будь-яку зовнішню статистику.

## 7. Резервне копіювання під час пілоту

Раз на тиждень: **Налаштування → Резервна копія → Завантажити (JSON)**.
Зберігати файли поза Render (безкоштовний план БД видаляється через 90 днів;
для бойового контуру — платний план з PITR, див. `docs/DEPLOY.md`).
