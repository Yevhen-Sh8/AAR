# AAR v1.1 — Context Accumulation Layer (Design Doc)

> **Статус**: Design draft, не імплементовано.
> **Тригер**: стаття Yaroslav Klochnyk (Senior Technical Architect, SoftServe)
> *«AI Agents in the SDLC: Why Task Automation Is No Longer Enough»* —
> [LinkedIn Pulse, 13 травня 2026 р.](https://www.linkedin.com/pulse/ai-agents-sdlc-why-task-automation-longer-enough-yaroslav-klochnyk-pmy8f).

## 1. Контекст

Поточна реалізація AAR v1.0 правильно вирішує **task execution**: тригери
формують кейси, LLM генерує драфт аналізу, рекомендації мають lifecycle
`proposed → in_progress → done → validated`.

Чого бракує — **systematic context accumulation**. Кожен LLM-виклик
(`classify_reason`, `draft_case_analysis`, `find_analogies`) видає корисний
side-channel знань (бізнес-правила, edge cases, failure patterns), які
**не зберігаються структуровано** — вони лишаються в межах одного кейсу
як вільний текст у `summary` або зникають разом із контекстним вікном.

Клочник формулює це так:

> «If every AI interaction ends only with a task output, we get speed,
> but we do not accumulate knowledge. It is like hiring a very smart
> consultant who quickly solves a problem, but leaves no notes,
> no blueprints, and no explanation of why the solution was designed
> this way.»

## 2. Принцип

> **Agent → Task Output + Reusable Context Asset → Shared Context Layer
> → Next Task Starts Smarter**

Кожен AI-агент у нашій системі повинен повертати **два результати**:

1. **Task output** — те, що повертає вже зараз (markdown-аналіз, код
   причини, ранкінг аналогів).
2. **Reusable context assets** — структуровані знання-фрагменти зі
   статусом, джерелом, власником і прапорцем повторного використання.

## 3. Чим це **не є**

| Помилкове ототожнення | Чим воно насправді відрізняється |
|---|---|
| Документація | Документація створюється post-fact, активи — **в момент виконання** |
| Agent memory (Anthropic memory tool) | Memory — приватна пам'ять одного агента; активи **спільні** між агентами, ролями, командами |
| `summary` поля у кейсі | `summary` — людський наратив; активи — structured records зі схемою |
| Audit log | Аудит фіксує **що сталося**; активи — **що тепер відомо** |

## 4. Маппінг на NATO LL Handbook 4

Найважливіше відкриття: наш базовий методологічний документ
([`docs/normative/nato-ll.md`](../normative/nato-ll.md)) уже описує
**той самий цикл**, який пропонує Клочник. Терміни співпадають один-в-один:

| Клочник (industry SDLC) | NATO LL Handbook 4 | AAR v1.0 (зараз) | AAR v1.1 (план) |
|---|---|---|---|
| Task output | Observation | LLM-результат у відповіді | `LLMResult.task_output` |
| Draft context asset | Lesson Identified (LI) | — (втрачається) | `ContextAsset(status="draft")` |
| Validated context asset | Lesson Learned (LL) | `KnowledgeEntry` (порожня) | `ContextAsset(status="validated")` |
| Reusable for X | Institutionalization | — | `reusable_for=["…"]` |
| Deprecated | Superseded LL | — | `ContextAsset(status="deprecated", superseded_by=…)` |

**Висновок**: v1.1 — це не «нова ідея», а **доведення NATO LL-циклу до
кінця** у нашій реалізації. Клочник дав сучасну назву і шаблон.

## 5. Сутність `ContextAsset`

```python
class ContextAssetType(StrEnum):
    BUSINESS_RULE = "business_rule"              # обмеження домену
    FAILURE_PATTERN = "failure_pattern"          # повторюваний механізм відмови
    EDGE_CASE = "edge_case"                      # неочевидний сценарій
    ACCEPTANCE_CRITERION = "acceptance_criterion"  # шаблон валідації
    ARCHITECTURAL_DECISION = "architectural_decision"
    DEPLOYMENT_LESSON = "deployment_lesson"
    OPERATOR_PRACTICE = "operator_practice"      # перевірена дія обслуги
    TRAINING_GAP = "training_gap"                # виявлений пропуск у підготовці


class AssetStatus(StrEnum):
    DRAFT = "draft"                  # видобуто агентом, не перевірено
    VALIDATED = "validated"          # підтверджено власником
    DEPRECATED = "deprecated"        # замінено новішим
    REJECTED = "rejected"            # відкинуто валідатором


class ContextAsset(Base):
    __tablename__ = "context_assets"
    id: int
    type: ContextAssetType
    title: str
    description: str               # коротке твердження (≤ 500 chars)
    source: str                    # "case:42" | "event:1337" | "report:7"
    source_agent: str | None       # "classify_reason" | "draft_analysis" | "manual"
    status: AssetStatus            # default = draft
    reusable_for: list[str]        # ["qa_agent", "operator_training", "deployment"]
    owner_role: Role               # хто має валідувати
    validated_by_user_id: int | None
    validated_at: datetime | None
    superseded_by_id: int | None   # для deprecated
    confidence: float | None       # 0..1, від LLM
    created_at: datetime
```

**Полі-перетин зі статтею Клочника** (буквальний — поля з його YAML-прикладу):

| YAML Клочника | Поле моделі |
|---|---|
| `type: business_rule` | `type` |
| `title: ...` | `title` |
| `description: ...` | `description` |
| `source: requirements_refinement` | `source` + `source_agent` |
| `status: validated` | `status` |
| `reusable_for: [...]` | `reusable_for` |

Плюс наші розширення: `owner_role`, `validated_by_user_id`, `superseded_by_id`,
`confidence` (потрібні для governance і автодеградації).

## 6. Зміни у LLM-сервісі

### Поточна сигнатура

```python
def draft_case_analysis(...) -> str:        # markdown
def classify_reason(...) -> ClassifyResult:  # {code, confidence, rationale}
def find_analogies(...) -> AnalogyResult:    # ранкінг
```

### Цільова сигнатура

```python
@dataclass
class LLMResult[T]:
    task_output: T                          # було єдиним результатом
    context_assets: list[ContextAssetDraft]  # NEW

def draft_case_analysis(...) -> LLMResult[str]: ...
def classify_reason(...)    -> LLMResult[ClassifyResult]: ...
def find_analogies(...)     -> LLMResult[AnalogyResult]: ...
```

**Промпт-зміна**: системний інструктаж для кожної функції додатково просить
повернути JSON-масив виявлених активів за схемою `ContextAssetDraft` (без
`id`/`validated_*` полів). Усі активи створюються зі `status='draft'`,
ніколи автоматично не `validated` (правило Клочника:
*«scaling mistakes»* — заборонено).

## 7. Validation lifecycle

```
        ┌─── reject ────┐
        ▼               │
   ┌─────────┐      ┌───┴───┐     ┌─────────┐
   │ draft   │─────▶│ valid │────▶│  used   │ (incremented usage_count)
   └─────────┘      └───┬───┘     └─────────┘
                        │
                        ▼  (з'являється кращий)
                  ┌──────────┐
                  │deprecated│  superseded_by → new asset id
                  └──────────┘
```

API:
- `POST /context/{id}/validate` — `Role.MANAGER` або `Role.ANALYST`
- `POST /context/{id}/reject` — з обов'язковою `reason`
- `POST /context/{id}/deprecate?superseded_by=N`
- Аудит-запис у hash-chain audit log при кожному переході.

## 8. Per-flow plan (за рекомендацією Клочника)

> *«I would not start with a large enterprise knowledge base. It is better
> to start with one SDLC flow.»*

Стартуємо з одного, найвужчого потоку — **AAR-кейс**:

| Крок поточного flow | Output | Які активи має лишити |
|---|---|---|
| Тригер створює кейс | `AARCase(status=open)` | — (тригер сам є активом раніше виявленим) |
| Учасник подає звіт | `IndividualReport` | candidate `edge_case`, `training_gap` |
| LLM генерує драфт | `draft_case_analysis()` markdown | `business_rule`, `failure_pattern`, `architectural_decision` |
| Менеджер фіналізує | `case.summary` | confirmation/rejection candidate assets |
| Recommendation → done | `Recommendation.validated_at` | `operator_practice`, `deployment_lesson` |
| Кейс закрито | `case.status=closed` | (нічого нового; усе вже у layer) |

## 9. Метрики flywheel (з статті — буквально)

Додати до місячного звіту нову секцію **«Context Flywheel»**:

| Метрика | Розрахунок |
|---|---|
| **Assets-per-task** | `count(ContextAsset) / count(AARCase)` за період |
| **Validation rate** | `validated / (validated + rejected + draft)` |
| **Reuse rate** | `Σ usage_count / count(validated assets)` |
| **Mean time to validate** | `avg(validated_at − created_at)` |
| **Cycle-time reduction** | `median(case.closed_at − opened_at)` місяць vs попередній |
| **Repeat-cause reduction** | T2 спрацювань цього місяця / попереднього |

Головне питання згідно з автором:
> «Did this task make the next task smarter, cheaper, and faster?»

→ операціоналізуємо у **single KPI**:
`SmartnessIndex = (Δ validation_rate + Δ reuse_rate − Δ cycle_time) ×100`

## 10. Дешевизна впровадження

| Складова | Стан |
|---|---|
| Сутність-аналог (`KnowledgeEntry`) | Уже існує, переписуємо у `ContextAsset` |
| Validation lifecycle | Уже є на `Recommendation` — патерн копіюємо |
| LLM-інфраструктура | Уже є з prompt caching і structured outputs |
| Аудит для змін статусу | Уже є hash-chain audit log |
| RBAC для `validate`/`reject` | Уже є `require_role(...)` |
| Метрики | Місячний звіт уже має caркac; додаємо новий розділ |

**Estimate**: 2–3 дні роботи на MVP, 1 тиждень на повну реалізацію з UI
для валідації активів.

## 11. Ризики (явно з статті)

1. **«Scaling mistakes»**: якщо невалідовані активи стають source of truth —
   організація масштабує помилки. **Mitigation**: за замовч. `draft`, ніколи
   не використовується автоматично; `find_analogies` шукає лише серед
   `status='validated'`.
2. **Shared confusion layer** замість shared context layer: якщо немає
   стандартизованих полів і власників. **Mitigation**: жорстка Pydantic-схема,
   обов'язковий `owner_role`.
3. **Інформаційний шум**: занадто багато активів → агент захлинається.
   **Mitigation**: `find_analogies` обмежує top-N за релевантністю; periodic
   review для `deprecate` старих/невикористовуваних.
