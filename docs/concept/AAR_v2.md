# Концепція AAR v2.0

> Розширення базової концепції AAR (v1.0, презентація 2025) модулем
> **«Облік і ефективність виробів»**, який живиться пономерною подійністю
> та автоматично породжує AAR-кейси за тригерами.

## 1. Маніфест (зберігається з v1.0)

- Цикл безперервного навчання: **Виконання → Аналіз → Висновки → Застосування**.
- Кожна подія — джерело знань.
- Фокус на причинах, а не симптомах.
- Аналіз є повним, а не вибірковим: усі учасники подають звіт.
- Стандартизація = якісний аналіз.
- База знань як інституційна пам'ять — не залежить від кадрових змін.

## 2. Дворівнева модель даних

```
┌──────────────────────────────────────────────────────────┐
│ Рівень 2. AAR-кейс (якісний)                             │
│ Що сталося / Що спрацювало / Що ні / Чому / Що змінити   │
│ Підсумковий аналіз, рекомендації, посилання у базу знань │
└────────────────────────▲─────────────────────────────────┘
                         │ агрегація + тригери
┌────────────────────────┴─────────────────────────────────┐
│ Рівень 1. Подія (структурована)                          │
│ Виріб (серійний №) · Тип · Експлуатант · Дата · Результат│
│ Причина (а–д для втрат / а–р для ремонту) · Зона відповід.│
└──────────────────────────────────────────────────────────┘
```

Подія — атомарна, незмінна (append-only). Кейс — мутабельний контейнер
аналітики над групою подій.

## 3. Модуль «Облік і ефективність виробів»

### 3.1. Довідники

| Довідник | Зміст | Адміністратор |
|---|---|---|
| `ItemType` | Тип виробу (А, Б, …) | Адмін |
| `Operator` | Експлуатанти (Е-01…Е-10), обслуги | Адмін |
| `LossReason` | Причини безповоротних втрат, коди а–д | Адмін |
| `RepairReason` | Причини повернення в ремонт, коди а–р | Адмін |
| `ResponsibilityZone` | Зона: обслуга / виробництво / зовнішнє | Адмін |
| `OutcomeStatus` | Запущено / Втрачено / На ремонт / Успіх | Системний |

### 3.2. Ключові показники

| Показник | Формула | Призначення |
|---|---|---|
| **Кеф** | У / З | Загальна ефективність використання |
| **Кеф_обсл** | У / (З − Вб_зовн − Вб_вир) | «Очищений» від не залежних від обслуги факторів |
| **Кв_обсл** | Втрати «зони обслуги» / З | Частка втрат, що залежать від обслуги |
| **Δ Кеф** | Кеф_міс − Кеф_попер_міс | Тренд |

### 3.3. Форми звітності

- **Щоденна довідка** (Т.1–Т.3) — див. [`docs/forms/daily-template.md`](../forms/daily-template.md)
- **Місячна звітність по експлуатантах** (Т.4–Т.7) —
  див. [`docs/forms/monthly-template.md`](../forms/monthly-template.md)

### 3.4. Тригери AAR-кейсу

Кейс відкривається автоматично, якщо:

1. **T1**: Кеф_обсл експлуатанта < поріг (за замовч. 70 %) три доби поспіль.
2. **T2**: Та сама причина (з а–д або а–р) повторилася ≥ N разів за вікно
   7 діб (N налаштовується).
3. **T3**: Аномалія по конкретному серійному № (множинні повернення в ремонт
   того ж виробу).
4. **T4**: Падіння Кеф підприємства > 10 в.п. за добу.
5. **T5**: Ручне ініціювання менеджером.

## 4. Ролі (доповнено v1.0)

| Роль | v1.0 | v2.0 — додаток |
|---|---|---|
| Учасник | подає звіт по операції | + може бути експлуатантом, що звітує по виробах |
| Менеджер AAR | узагальнення кейсу | + підтверджує авто-згенеровані тригерами кейси |
| Адміністратор | налаштування системи | + веде довідники причин і типів виробів |
| **Аналітик підприємства** *(нова)* | — | формує щоденні/місячні довідки, ескалює критичні відхилення |
| **Системний інтегратор** *(нова)* | — | відповідає за CSV/REST джерела даних з виробництва |

## 5. Автоматизація

Окремий розділ [`docs/automation.md`](../automation.md) описує 12 сценаріїв
A1–A12: прийом подій, валідація, обчислення Кеф, генерація довідок, тригери
AAR, нагадування, LLM-класифікація причин, генерація драфту висновків,
пошук аналогій, експорт у формати наказу № 440, аудит.

## 6. Нормативна сумісність

Платформа має продукувати документи, сумісні за реквізитами та формою з:

- Наказом Міноборони № 440 (редакція 25.04.2025) — електронний облік
  військового майна.
- Наказом № 90 (зі змінами z1486-25).
- Наказом № 687 від 14.10.2024 — облік особового складу (для довідника
  обслуг).

Методологічна основа AAR — NATO Lessons Learned Handbook, 4th Edition
(JALLC, 2022) та JALLC Analysis Handbook (2024). Деталі та мапи —
у [`docs/normative/`](../normative/).

## 7. Архітектурні принципи (з v1.0)

- **Offline-first**: повний функціонал без мережі (PWA + IndexedDB).
- **Локальне збереження** на пристрої експлуатанта; авто-синхронізація.
- **Гнучкі форми**: секції, поля та класифікатори редагуються адмінкою.
- **Зручність**: 1–2 кліки на ключові дії, авто-збереження чернеток.
- **Стандартизація**: єдиний формат подій і кейсів у межах організації.

## 8. Інтеграція рівнів — приклад end-to-end

1. Експлуатант Е-07 запускає за добу 12 виробів типу А.
2. 3 виробів повернулися в ремонт, причина «помилка розрахунку»
   (зона: обслуга).
3. Подія `UsageEvent` × 12 надходить до системи (CSV-імпорт о 23:00).
4. О 23:59 cron генерує щоденну довідку: Кеф = 75 %, Кеф_обсл = 75 %.
5. Третій день поспіль Кеф_обсл нижче порога → спрацьовує тригер T1.
6. Автоматично створюється AAR-кейс «Е-07 / зниження Кеф_обсл / тип А».
7. LLM генерує драфт: контекст, перелік пов'язаних подій, гіпотези причин,
   рекомендовані запитання учасникам.
8. Менеджер уточнює, надсилає індивідуальні форми обслузі Е-07.
9. Після збору відгуків — підсумковий аналіз, рекомендація: довчання на
   тренажері за модулем «розрахунок пуску».
10. Запис іде в базу знань. При плануванні наступного місяця система
    знаходить аналогії та підсвічує ризик для інших обслуг.

## 9. Що **не** є у скоупі v2.0

- Інтеграції з DELTA / «Кропива» / SAP / «Оберіг» — Етап 9 (опціонально).
- Мобільні нативні застосунки — лише PWA.
- Геопросторовий шар (мапа застосування) — наступна версія.
