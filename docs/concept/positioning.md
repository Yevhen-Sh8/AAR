# Позиціонування AAR та проактивна взаємодія

> Джерело: два концептуальні документи користувача (липень 2026):
> «Особливості AAR та відмінності порівняно з існуючими системами» та
> «Проактивна взаємодія та підтримка підготовки до виконання завдань».
> Цей файл — канонічна фіксація обох у репозиторії; статус реалізації
> кожного пункту — в таблицях нижче.

## 1. Відмінні особливості рішення

Система вирізняється комплексним підходом до збору, аналізу та повторного
використання досвіду. На відміну від звичайного підсумкового звіту однієї
посадової особи, вона залучає безпосередніх учасників подій, збирає їхні
індивідуальні спостереження та об'єднує їх у структурований фінальний звіт.

| Особливість з концепції | Статус | Де в системі |
|---|---|---|
| Орієнтація на досвід безпосередніх учасників | ✅ | `IndividualReport` (6 блоків), анонімний режим (TC 25-20) |
| Поетапний збір індивідуальних оцінок від визначених учасників | ✅ | `POST /aar/cases/{id}/request-reports` — розсилка запитів, pending→submitted |
| Зіставлення різних поглядів на перебіг подій | ✅ | Список звітів у кейсі + LLM-синтез (`/llm/cases/{id}/draft-analysis`) |
| Узагальнені висновки на основі досвіду учасників, не однієї особи | ✅ | LLM-чернетка аналізу з усіх звітів → людське редагування (`analysis`, ADR-011) |
| Централізована база проблем, успішних дій, рішень, рекомендацій | ✅ | Context Accumulation Layer (`ContextAsset`, draft→validated, ADR-007/008) |
| Повторне використання досвіду в аналогічних завданнях | ✅ | `find_analogies` по validated-активах (ADR-009) |
| Адаптація структури звіту до типу завдання/ролей | ⚠️ частково | NATO-поля кейсу універсальні; шаблони за типами завдань — бэклог |
| Єдиний стандартизований процес AAR | ✅ | NATO state machine open→…→closed (Wave 1, ADR-010) |

## 2. Відмінності від аналогів

Наявні на ринку рішення покривають окремі напрями: запис/відтворення навчань,
сховища звітів, аналіз технічних інцидентів (post-incident review),
накопичення окремих висновків. **Перевага нашої системи — не одна унікальна
функція, а поєднання** в одному рішенні: структурований AAR-процес +
індивідуальні оцінки учасників + кероване узагальнення + накопичення
організаційного досвіду + вимірювання самого циклу навчання (learning-loop
KPI, Wave 2) + пономерна об'єктивна телеметрія виробів (Рівень 1), якої
класичні AAR-платформи не мають взагалі.

## 3. Перспективи розвитку (з концепції → статус)

| Перспектива | Статус |
|---|---|
| ШІ для узагальнення оцінок учасників | ✅ реалізовано (draft-analysis) |
| Автовиявлення повторюваних проблем і типових помилок | ✅ тригер T2 + автовалідація/регресія рекомендацій |
| Пошук аналогічних ситуацій у базі досвіду | ✅ find_analogies (ADR-009) |
| Формування рекомендацій на основі накопичених даних | ✅ Recommendation + LLM-чернетки |
| Виявлення тенденцій у діяльності підрозділів | ✅ тригери T1/T4, monthly trends, learning-loop KPI |
| Інтеграція з системами планування та управління | ✅ webhook-шар (ODIN/DELTA/Kropyva/SAP; Оберіг виключено — ADR-003) |

## 4. Проактивна взаємодія (реалізовано у Wave 6)

Система використовується **не лише після** завершення завдання (класичний
AAR), а й **на етапі підготовки** до нього:

- Будь-який користувач може заздалегідь додати **попередження про ризик,
  виявлену проблему, пропозицію або інформаційний сигнал**.
- Сигнали реєструються в системі та передаються відповідальним особам на
  розгляд: *прийняти* (враховано в підготовці), *відхилити* (з причиною),
  або *перетворити на повноцінний AAR-кейс*.
- Допускається анонімне подання (та сама blame-free логіка TC 25-20, що й
  для індивідуальних звітів — ADR-015).

Так формується **безперервний цикл організаційного навчання**:

```
        ┌──────────── ПІДГОТОВКА ────────────┐
        │  Проактивні сигнали (Wave 6)       │
        │  warning / risk / proposal / info  │
        │  + validated-активи з бази досвіду │
        └──────────────┬─────────────────────┘
                       ▼
                 ВИКОНАННЯ ЗАВДАННЯ
                       │  (пономерні події, Рівень 1)
                       ▼
        ┌──────────── АНАЛІЗ (AAR) ──────────┐
        │  Кейси → NATO-цикл → уроки (LL)    │
        │  → рекомендації → автовалідація    │
        └──────────────┬─────────────────────┘
                       ▼
              ЦЕНТРАЛІЗОВАНА БАЗА ДОСВІДУ
                       │
                       └──────► назад у ПІДГОТОВКУ
```

Реалізація: модель `PreTaskSignal` (kind: warning/risk/proposal/info; статуси
new → acknowledged → accepted/dismissed/converted), роутер `/signals`
(подання, розгляд, конвертація в кейс з передзаповненим `what_happened`),
сторінка «Сигнали (до завдання)» в UI, webhook `signal.created`, аудит-дії
`signal.created/reviewed/converted`. Див. `docs/PLATFORM.md` §4 Wave 6.

## 5. Чому класична AAR «дає лише ~22%» — і як ми піднімаємо цю планку

### Правильне прочитання цифри

Мета-аналіз Tannenbaum & Cerasoli (2013, Human Factors, 46 досліджень):
**правильно проведений** дебриф/AAR покращує результативність команди на
**20–25%** у середньому. Тобто ~22% — це не «стеля неефективності», а
**приз за коректне виконання**, який більшість організацій не забирає,
бо процес ламається ПІСЛЯ дебрифу: урок фіксується (Lesson Identified),
але не впроваджується й не валідується (Lesson Learned). Саме цю
конверсію LI→LL NATO-структури історично не вимірюють — тому й «не
звертають уваги».

### Недоліки класики → наші механізми

| # | Недолік класичної AAR | Наша відповідь |
|---|---|---|
| 1 | Тільки наратив, без об'єктивних даних | Рівень 1: пономерна телеметрія (MSR/η_c/λ_c) під кожним кейсом |
| 2 | LI ≠ LL — уроки не впроваджуються | NATO state machine + автовалідація/авторегресія рекомендацій |
| 3 | Немає відповідального | Обов'язковий OPR + дашборд навантаження |
| 4 | Write-only архів | Пошук аналогій по validated-активах (ADR-009) |
| 5 | Культура звинувачення → мовчання | Анонімні звіти й сигнали (ADR-015) |
| 6 | Ніхто не міряє сам цикл навчання | Learning-loop KPI: time-to-validation, % LI→LL, recurrence |
| 7 | Реактивність (тільки після події) | Проактивні сигнали до завдання (Wave 6) |
| 8 | Дорого проводити (фасилітатор, години) | LLM-чернетка синтезу за секунди, людина затверджує |

### Стратегія прийняття на постачання (планувальники операцій/місій)

1. **Продавати конверсію, а не архів** — дашборд «Цикл навчання» дає
   командуванню цифру, якої класична AAR не має: «X% уроків доведено до
   підтвердженої зміни за Y днів».
2. **Пілот із базовою лінією** — 60–90 днів на одному підрозділі:
   MSR/recurrence «до» → система → дельта «після». Власний доведений
   «+22%» на своїх даних — головний аргумент постачання.
3. **«Брифінг підготовки місії» (наступна хвиля)** — планувальник вводить
   тип завдання/сектор → система автоматично видає: релевантні validated
   уроки + активні сигнали + статистику виробів по профілю. AAR стає
   ВХОДОМ у планування, а не звітом після.
4. **Вбудовування, не заміна** — NATO-термінологія в моделі даних,
   експорти за наказом №440, вебхуки в ДЕЛЬТА/Кропиву: система вписується
   в наявний штабний цикл.

JALLC Lessons Learned (jallc.nato.int/activities/lessons-learned);
